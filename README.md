# Headless Blender Character Builder

Build an original geometric character from bounded JSON, then open the real
Blender scene, use the GLB, or inspect a print-oriented STL. The primary path
runs headlessly in Docker: no host Blender installation, AI key, or provider
account is required.

![Facet Bot generated by the headless Blender pipeline](docs/assets/facet-bot-preview.png)

This preview is not a generated illustration. It is an optimized copy of
`preview.png` from a passing containerized Blender build. The same build
produced a reopenable `.blend`, GLB, a single-shell STL, three diagnostic
views, geometry QA, and a hash manifest. The tracked
[asset manifest](docs/assets/manifest.json) records its provenance and CC0
license.

> **First-release support boundary:** v0.1.0-rc.1 is a source candidate for a trusted user building
> their own models locally with the one-shot Docker builder. Here, “trusted”
> means that you control the machine and create or review the bounded JSON
> request. The optional Compose service is experimental, local-only, and for
> one trusted operator. Internet-facing, multi-tenant, and VPS operation are
> outside v0.1 support. The repository does **not** yet publish a GitHub Release,
> container images, or a hosted service. No project package is published on PyPI,
> and installing a similarly named package from PyPI is not supported.

## Build your first model

You need Git, Docker Engine or Docker Desktop, GNU Make, about four CPU cores,
8 GB RAM, and 10 GB of free disk. Start Docker, then run:

```sh
git clone https://github.com/joseph-robert-f/headless-blender-character-builder.git
cd headless-blender-character-builder
./scripts/doctor
make build REQUEST="$PWD/examples/requests/facet-bot.json" OUTPUT_NAME=facet-bot
make verify REQUEST="$PWD/examples/requests/facet-bot.json" OUTPUT_NAME=facet-bot
```

The first build needs network access while Docker downloads the pinned base
image, Blender 4.5.12 LTS, and Debian packages. Model generation and
verification run later in fresh containers with networking disabled.

A successful run ends with:

```text
BUILDER_BUILD: PASS
BUILDER_VERIFY: PASS
```

Your model is in `build/facet-bot/`. Start with `preview.png`, then choose the
artifact that fits your next step:

| Artifact | What to do with it |
|---|---|
| `model.blend` | Open and inspect the scene in Blender 4.5.12 LTS. Display meshes remain separate; the printable shell is `PRINT/PrintableShell`. |
| `model.glb` | Preview the display model in a GLB viewer or import it into a compatible 3D tool or engine. |
| `model.stl` | Open the single-shell export in a slicer. Select **millimeters** explicitly because STL files do not store units. |
| `preview.png` | See the beauty render without opening a 3D application. |
| `diagnostics/*.png` | Compare the front, side, and back geometry views. |
| `qa.json` | Read the measured geometry checks and terminal QA status. |
| `manifest.json` | Audit request, generator, Blender, execution, size, and SHA-256 provenance for the other eight artifacts. |

Run `make inspect OUTPUT_NAME=facet-bot` for a bounded, path-free manifest and
QA summary. This is a convenient read-only view; `make verify` remains the
independent artifact check.

The builder refuses to overwrite an existing output. Keep a result by moving
it aside, or choose a new output name:

```sh
mv build/facet-bot build/facet-bot.previous
make build REQUEST="$PWD/examples/requests/facet-bot.json" OUTPUT_NAME=facet-bot
```

For macOS setup without Homebrew, Linux, experimental WSL2, direct Docker
commands without Make, native Blender, updates, and cleanup, follow the
[installation guide](docs/installation.md).

## Make it yours

Requests choose a reviewed generator and bounded modeling parameters; they do
not contain code, paths, URLs, add-ons, or Blender flags. Copy the example into
the ignored build area, edit the documented fields, and give each run a unique
lowercase, hyphenated output name:

```sh
mkdir -p build/requests
cp examples/requests/facet-bot.json build/requests/my-character.json
# Edit build/requests/my-character.json using docs/character-spec.md.
make validate REQUEST="$PWD/build/requests/my-character.json"
make build REQUEST="$PWD/build/requests/my-character.json" OUTPUT_NAME=my-character
make verify REQUEST="$PWD/build/requests/my-character.json" OUTPUT_NAME=my-character
```

Start with [the examples and project ideas](examples/README.md), then use the
[configuration reference](docs/configuration.md) and
[character contract](docs/character-spec.md) for every supported field. The
bundled `moss-hopper` request is intentionally a fail-closed QA example:
ambiguous wall evidence returns `needs_review` instead of publishing a
successful artifact tree.

Good fits for this v0.1 generator include:

- original desk mascots and geometric creatures;
- repeatable GLB fixtures for viewers, engines, and asset pipelines;
- print-oriented prototypes to review in a slicer before test printing;
- classrooms or workshops that need inspectable procedural geometry; and
- CI demonstrations where a PNG alone is not enough proof.

It is not unrestricted prompt-to-3D, organic sculpting, protected-character
replication, arbitrary Blender automation, or a guarantee that a physical
print will succeed.

## How the model is proved

Verification does more than check that files exist:

- a fresh Blender process reopens `model.blend` with factory startup settings;
- it enumerates mesh objects, vertices, faces, materials, finite transforms,
  and three-dimensional bounds;
- it imports GLB and STL into clean scenes and compares their geometry with
  the evaluated Blender scene;
- the STL must be one face-connected, watertight, outward-oriented shell with
  positive volume, no non-manifold edges, and no zero-area faces; and
- it recomputes every artifact byte count and SHA-256 before accepting the
  manifest.

These checks establish that the output is a real, internally consistent model.
They do not replace slicer settings, material selection, printer calibration,
supports, or physical testing.

emulation and is suitable for evaluation; Linux `arm64` is best effort, and

## Optional asynchronous service

> **Experimental and local-only:** use this stack on loopback with one trusted
> operator and requests you created or reviewed. It is not a supported v0.1 path
> for Internet-facing, multi-user, or hostile-input workloads.

The service adds an authenticated API, PostgreSQL, Redis, versioned
S3-compatible local storage, and one Blender worker. It invokes the same
builder contract and still needs no AI-provider key.

If `python3 --version` is older than 3.11, first run
`export PYTHON=python3.11` (or another installed 3.11+ executable) for this
terminal session.

```sh
./scripts/doctor --service
make init-env
make service-config
make service-up
make service-ps
```

`service-ps` should show `api`, `worker`, PostgreSQL, Redis, and MinIO running;
the one-shot `database-init` and `minio-init` rows should say `Exited (0)`. Now
submit the bundled request and save one verified result:

```sh
make service-client REQUEST="$PWD/examples/requests/facet-bot.json"
```

When finished, stop this
checkout's stack with `make service-down`.

`make init-env` creates an ignored mode-`0600` `.env` once and refuses to
overwrite it. It records a checkout-specific Compose project name, so two fresh
checkouts do not share containers or named volumes. Move the checkout together
with its `.env` to retain that identity; existing `.env` files created before
this field was added continue to use the legacy `hbcb-local` project and preserve
their volumes. The API and artifact downloads bind to host loopback;
PostgreSQL and Redis are not published. The worker container has only its
required internal service networks. Its fresh Blender child receives a
scrubbed environment without API, database, queue, storage, provider, or
Docker credentials, but it shares the supervisor container's network
namespace—it is not separately network-isolated.

The local MinIO image is a pinned compatibility fixture, not a production
object-store recommendation. Do not expose this stack publicly. Read
the [lightweight HTTP API client](docs/api.md#lightweight-local-client),
[troubleshooting](docs/troubleshooting.md), [architecture](docs/architecture.md),
and the [VPS availability note](docs/deployment.md#availability) before
integrating or operating it.

`make service-client` is the documented first-evaluation and custom-request
path for this experimental stack. `make service-smoke` is the
slower maintainer/integration confidence gate: it performs direct and service
builds, restarts the API, tests cancellation and IAM, and retains evidence. It
can add another 4 GiB builder workload, so allocate at least 12 GiB to Docker
before running it.

## Security, rights, and print limits

- The normal builder accepts only schema-validated declarative JSON. Uploaded
  `.blend` files, request-authored Python or shell, archives, remote URLs, host
  paths, and add-ons are rejected or out of scope.
- One-shot build and verify containers run non-root with no network, a
  read-only root filesystem, dropped capabilities, and bounded resources.
- Blender is treated as trusted generator code, not as a sandbox for hostile
  scripts or files.
- STL numeric coordinates are millimeters, but STL itself carries no unit
  metadata. Automated QA cannot certify a model as safe, durable, food-safe,
  child-safe, medical, electrical, or load-bearing.
- You are responsible for rights to designs, names, references, logos,
  likenesses, and outputs. This project grants no rights to Pokémon or any
  other third-party character or brand.
- v0.1 support covers the trusted local one-shot builder. The optional local
  service is experimental; public, multi-tenant, and VPS operation remain out
  of scope. There is no billing system, SLA, automatic IP clearance, or
  print-success warranty.

Read [OUTPUT_POLICY.md](OUTPUT_POLICY.md), [SECURITY.md](SECURITY.md), and
[SUPPORT.md](SUPPORT.md). Report vulnerabilities through
[GitHub private vulnerability reporting](https://github.com/joseph-robert-f/headless-blender-character-builder/security/advisories/new),
not a public issue.

## Develop and verify the project

Common maintainer commands are:

```sh
make test-unit          # contracts, policies, service units, and security tests
make test-blender       # real headless Blender integration gates
make check              # lint/static, unit/security, and Blender checks
make dependency-check   # verify synchronized dependency pins offline
make dependency-audit   # report upstream version/image status without mutation
make dependency-scan    # vulnerability-scan locks and release images
make release-static     # audit tracked source, policies, licenses, docs, and CI
HBCB_RELEASE_RUN_ID=review-1 make release-check  # complete clean-index gate
```

The release run ID is mandatory and must be unique among checkouts sharing a
Docker daemon. `make release-check` builds local evidence and versioned image tags from a
clean export of the Git index. It never pushes images, creates a Git tag or
Release, deploys infrastructure, or reads registry credentials. See the
[release process](docs/release-process.md) and
[dependency maintenance guide](docs/dependency-maintenance.md).
